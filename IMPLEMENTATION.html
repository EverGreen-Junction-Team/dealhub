1. Executive summary

A private GoHighLevel marketplace app installed on your sub-account receives every opportunity-related event in real time, enriches it with conversation data, contact details and custom fields, then writes structured rows into a self-hosted Postgres database (Supabase) running on a dedicated EU server.

The end state is a queryable history of every pipeline movement, every message exchanged in each stage, and every contact / opportunity custom field — without ever exporting a CSV manually. SQL queries on top answer the analytics questions you raised: stage velocity, conversion funnels, per-sales-manager segmentation, message delivery rates, and stage-by-stage comparisons.

What's live today: webhook ingestion, 7-table schema, real-time stage history, message capture with delivery status, contact / opportunity custom fields, daily orphan sweep, HTTPS via custom domain.

3. Webhook subscriptions

GoHighLevel pushes seven opportunity-related events to a single URL: https://app.pipelineegj.com/webhooks/ghl. Each event is dispatched to a different code path. Three events affect stage history, four are metadata-only.

EventTriggers whatWrites opportunities?Writes stage_history?Fetches messages?
OpportunityCreateNew opp created✅ insert✅ open first row❌ (empty window)
OpportunityStageUpdateStage transition✅ refresh✅ close prior + open new✅ messages from closing stage
OpportunityDeleteOpp deleted✅ is_deleted = true✅ close current row❌
OpportunityUpdateGeneric edit (custom field, name, etc.)✅ refresh❌❌
OpportunityStatusUpdateopen → won / lost / abandoned✅ status refresh❌❌
OpportunityAssignedToUpdateOwner reassigned✅ assigned_to refresh❌❌
OpportunityMonetaryValueUpdate$ value edited✅ monetary_value refresh❌❌
INSTALL / UNINSTALLApp installed / removedn/an/an/a — token storage only

Every webhook is RSA-signature verified against GoHighLevel's published public key before processing. Duplicate deliveries are deduped via a processed_events table that uniques on webhookId.

Four customer-data tables (with Row-Level Security per location_id) and three operational tables. Every row carries location_id so multi-tenant separation is enforced at the database level.

4.6 pending_opportunities Live · internal

Orphan queue. When an opp is created we add a row here; when it later moves stage / status / anything, we remove it. The daily sweep cron runs at 03:00 UTC and emits a synthetic stage_history row for anything still in the queue past a 10-minute cool-off — so opportunities that have been sitting since creation still appear in your data.

4.7 processed_events Live · internal

Idempotency log. Every incoming webhook's webhookId is inserted before processing; the UNIQUE constraint deduplicates GHL's retry deliveries silently. Rows TTL'd to 14 days.

5. Behaviour cases

Concrete examples of what lands in each table for the most common real-world scenarios.

5.1 New opportunity created (no messages yet)

T1 — GHL fires OpportunityCreate
→ contacts: 1 row inserted/refreshed
→ opportunities: 1 row inserted (current_stage_name + first_stage_name = "Initial contact made")
→ stage_history: 1 row opened (entered_at=T1, current_stage=true)
→ messages: 0 (window is empty)
→ pending_opportunities: 1 row queued

5.2 Stage transition (after exchanging messages)

T1 — opp created at the "Initial contact made" stage
stage_history row1 opens with stage_name = "Initial contact made"
T1 → T5 — 6 messages exchanged
No webhook fires for messages alone — our DB stays unchanged
T5 — GHL fires OpportunityStageUpdate ("Initial contact made" → "Qualified")
→ We fetch all messages exchanged in the window [T1, T5]
→ All 6 messages persisted, each linked to row1 (the closing stage)
→ row1 closed: left_at=T5, in_stage_duration_seconds = T5−T1
→ row2 opened: entered_at=T5, stage="Qualified"
→ Removed from orphan opportunities — some communication happened, so the deal is no longer "stuck since creation"

5.3 Status change without stage movement

E.g. you mark an opp lost directly without moving it through stages.

T8 — GHL fires OpportunityStatusUpdate (status: open → lost)
→ opportunities.status refreshed to "lost"
→ stage_history: no new row (stage didn't change)
→ messages: not refreshed (metadata-only event)

5.4 Custom field / monetary value / assignment edits

Any time you edit an opp in GHL without moving it, the corresponding metadata-only webhook fires.

EditWebhookEffect
£ value changedOpportunityMonetaryValueUpdateopportunities.monetary_value refreshed
Owner reassignedOpportunityAssignedToUpdateopportunities.assigned_to + assigned_to_name refreshed
Custom field editedOpportunityUpdateFull row refreshed including custom_fields JSONB

5.5 Orphan opportunity (created but never moved)

T1 — opp created
row added to pending_opportunities
T1 + 24h — opp still sitting, no stage move, no edits
Daily sweep cron at 03:00 UTC notices the orphan
Cron run
→ Synthetic stage_history row emitted with triggered_by = 'daily_sweep'
→ Row removed from pending_opportunities (notified at most once)

5.6 Opportunity deleted

T10 — GHL fires OpportunityDelete
→ opportunities.is_deleted = true
→ Currently-open stage_history row closed with deleted = true, left_at = T10
→ Historical analytics rows (previous stages + messages) are PRESERVED — only marked deleted, not removed

6. Enrichment + data cleaning

6.1 Custom fields keyed by fieldKey

JSONB keys use the full GHL fieldKey (e.g. contact.pincode, opportunity.meddic_1). That's GHL's canonical identifier — stable across renames in the GHL UI, no ambiguity between contact and opp fields with the same short name.

// Example contacts.custom_fields JSONB:
{
  "contact.pincode": "SW1A 1AA",
  "contact.utm_source": "google",
  "contact.gclid": "Cj0KCQiA..."
}

// Example opportunities.custom_fields JSONB:
{
  "opportunity.product_system": "Crittall",
  "opportunity.product_type": "Bifold Door",
  "opportunity.meddic_1": "Champion identified"
}

6.2 Message body cleaning

ChannelWhat we stripWhat we keep
Email (HTML)Outer <html> / <head>, all <style> and <script> blocks, tracking pixels, common unsubscribe footers, all style and class attributesEverything inside <body> with semantic HTML preserved (links, images, structure)
SMS / WhatsAppEmoji icons (so reactions become readable text), GHL UI placeholders like >AUDIO< or >IMAGE<All real text — including reaction phrases like "Reacted to" minus the emoji

The message_body_raw column keeps the unmodified original so any "this body looks wrong" reports can be audited against the source for the first month.

7. SQL query library

Practical queries for the use cases you raised. Run them directly in the Supabase SQL editor or any Postgres client connected to the database.

7.1 Pipeline velocity — average time in each stage

SELECT
  stage_name,
  COUNT(*) FILTER (WHERE NOT current_stage) AS completed_occupancies,
  ROUND(AVG(in_stage_duration_seconds) FILTER (WHERE NOT current_stage) / 3600.0, 1) AS avg_hours,
  ROUND(PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY in_stage_duration_seconds)
        FILTER (WHERE NOT current_stage) / 3600.0, 1) AS median_hours,
  ROUND(PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY in_stage_duration_seconds)
        FILTER (WHERE NOT current_stage) / 3600.0, 1) AS p95_hours
FROM stage_history
GROUP BY stage_name
ORDER BY avg_hours DESC NULLS LAST;

7.2 Stalled deals — opps stuck in a stage longer than N days

SELECT
  o.name                                      AS opportunity_name,
  o.assigned_to_name                          AS owner,
  sh.stage_name                               AS stuck_in,
  sh.entered_at,
  EXTRACT(EPOCH FROM (now() - sh.entered_at)) / 86400 AS days_stuck,
  o.monetary_value
FROM stage_history sh
JOIN opportunities o
  ON o.location_id = sh.location_id AND o.opportunity_id = sh.opportunity_id
WHERE sh.current_stage = true
  AND o.is_deleted = false
  AND sh.entered_at < now() - interval '7 days'
ORDER BY days_stuck DESC;

7.3 Conversion funnel — stage-to-stage drop-off

WITH stage_entries AS (
  SELECT stage_name, COUNT(*) AS entered
  FROM stage_history
  GROUP BY stage_name
)
SELECT
  stage_name,
  entered,
  ROUND(100.0 * entered / MAX(entered) OVER (), 1) AS pct_of_top_stage
FROM stage_entries
ORDER BY entered DESC;

7.4 Win rate by starting stage

SELECT
  first_stage_name,
  COUNT(*)                                          AS total_opps,
  COUNT(*) FILTER (WHERE status = 'won')            AS won,
  COUNT(*) FILTER (WHERE status = 'lost')           AS lost,
  COUNT(*) FILTER (WHERE status = 'open')           AS still_open,
  ROUND(100.0 * COUNT(*) FILTER (WHERE status = 'won') / NULLIF(COUNT(*), 0), 1) AS win_pct
FROM opportunities
WHERE is_deleted = false
GROUP BY first_stage_name
ORDER BY win_pct DESC NULLS LAST;

7.5 Per-sales-manager — performance comparison

SELECT
  o.assigned_to_name,
  COUNT(*)                                          AS opps_owned,
  COUNT(*) FILTER (WHERE o.status = 'won')          AS won,
  ROUND(AVG(o.monetary_value), 2)                   AS avg_deal_size,
  SUM(o.monetary_value) FILTER (WHERE o.status = 'won')  AS won_revenue,
  ROUND(100.0 * COUNT(*) FILTER (WHERE o.status = 'won') / NULLIF(COUNT(*), 0), 1) AS win_pct
FROM opportunities o
WHERE o.is_deleted = false AND o.assigned_to_name IS NOT NULL
GROUP BY o.assigned_to_name
ORDER BY won_revenue DESC NULLS LAST;

7.6 Cross-user comparison at the SAME stage

"How do User A and User B compare at the Negotiation stage?"

SELECT
  o.assigned_to_name,
  COUNT(*)                                                          AS deals_at_stage,
  ROUND(AVG(EXTRACT(EPOCH FROM (now() - sh.entered_at)) / 86400), 1) AS avg_days_in_stage,
  COUNT(m.id)                                                       AS msgs_exchanged
FROM stage_history sh
JOIN opportunities o
  ON o.location_id = sh.location_id AND o.opportunity_id = sh.opportunity_id
LEFT JOIN messages m ON m.stage_history_id = sh.id
WHERE sh.stage_name = 'Negotiation'
  AND sh.current_stage = true
  AND o.is_deleted = false
GROUP BY o.assigned_to_name
ORDER BY deals_at_stage DESC;

7.7 Filter by opportunity type — only "Closed Won" deals

SELECT
  o.name, o.assigned_to_name, o.monetary_value,
  o.current_stage_name, o.first_stage_name,
  o.created_at_ghl, o.updated_at
FROM opportunities o
WHERE o.status = 'won'
  AND o.is_deleted = false
ORDER BY o.updated_at DESC;

7.8 Messages per stage — "what did we say to this customer in stage X?"

SELECT
  sh.stage_name,
  m.message_timestamp,
  m.message_direction,
  m.message_channel,
  m.message_status,
  LEFT(m.message_body, 200) AS body_preview
FROM messages m
JOIN stage_history sh ON sh.id = m.stage_history_id
WHERE sh.opportunity_id = 'OPP_ID_HERE'
ORDER BY m.message_timestamp;

7.9 Message delivery rate per stage (outbound SMS only)

SELECT
  sh.stage_name,
  COUNT(*)                                                 AS sent,
  COUNT(*) FILTER (WHERE m.message_status = 'delivered')   AS delivered,
  COUNT(*) FILTER (WHERE m.message_status = 'failed')      AS failed,
  ROUND(100.0 * COUNT(*) FILTER (WHERE m.message_status = 'delivered')
        / NULLIF(COUNT(*), 0), 1)                          AS delivery_pct
FROM messages m
JOIN stage_history sh ON sh.id = m.stage_history_id
WHERE m.message_direction = 'outbound'
  AND m.message_channel = 'SMS'
GROUP BY sh.stage_name
ORDER BY sent DESC;

7.10 Compare conversations across stages for one customer

"How does my conversation with Chris Spilsbury in Sales Qualified compare to in Negotiation?"

SELECT
  sh.stage_name,
  sh.entered_at,
  sh.left_at,
  COUNT(m.id) FILTER (WHERE m.message_direction = 'inbound')  AS inbound,
  COUNT(m.id) FILTER (WHERE m.message_direction = 'outbound') AS outbound,
  MIN(m.message_timestamp) AS first_msg,
  MAX(m.message_timestamp) AS last_msg
FROM stage_history sh
LEFT JOIN messages m ON m.stage_history_id = sh.id
WHERE sh.opportunity_id = 'OPP_ID_HERE'
GROUP BY sh.id, sh.stage_name, sh.entered_at, sh.left_at
ORDER BY sh.entered_at;

7.11 Lost opportunity analysis — where in the funnel they died

SELECT
  o.first_stage_name                AS started_in,
  o.current_stage_name              AS lost_at,
  COUNT(*)                          AS opps_lost,
  ROUND(AVG(EXTRACT(EPOCH FROM (o.updated_at - o.created_at_ghl)) / 86400), 1) AS avg_days_alive
FROM opportunities o
WHERE o.status = 'lost' AND o.is_deleted = false
GROUP BY o.first_stage_name, o.current_stage_name
ORDER BY opps_lost DESC;

7.12 Custom-field filter — opps for a specific product line

SELECT
  o.name, o.current_stage_name, o.status, o.monetary_value,
  o.custom_fields->>'opportunity.product_system' AS product_system,
  o.custom_fields->>'opportunity.product_type'   AS product_type
FROM opportunities o
WHERE o.custom_fields->>'opportunity.product_system' = 'Crittall'
  AND o.is_deleted = false
ORDER BY o.monetary_value DESC NULLS LAST;

7.13 UTM attribution — which sources convert best

SELECT
  c.utm_source,
  c.utm_campaign,
  COUNT(DISTINCT o.opportunity_id)                                              AS opps,
  COUNT(DISTINCT o.opportunity_id) FILTER (WHERE o.status = 'won')              AS won,
  SUM(o.monetary_value) FILTER (WHERE o.status = 'won')                         AS won_revenue,
  ROUND(100.0 * COUNT(DISTINCT o.opportunity_id) FILTER (WHERE o.status = 'won')
        / NULLIF(COUNT(DISTINCT o.opportunity_id), 0), 1)                       AS win_pct
FROM contacts c
JOIN opportunities o
  ON o.location_id = c.location_id AND o.contact_id = c.contact_id
WHERE c.utm_source IS NOT NULL
  AND o.is_deleted = false
GROUP BY c.utm_source, c.utm_campaign
ORDER BY won_revenue DESC NULLS LAST;

7.14 Full opportunity timeline — single deal, full history

SELECT
  sh.stage_name,
  sh.entered_at,
  sh.left_at,
  sh.in_stage_duration_seconds / 3600.0    AS hours_in_stage,
  sh.current_stage,
  sh.triggered_by,
  (SELECT COUNT(*) FROM messages m WHERE m.stage_history_id = sh.id) AS messages
FROM stage_history sh
WHERE sh.opportunity_id = 'OPP_ID_HERE'
ORDER BY sh.entered_at;

8. Operational notes

8.1 Multi-tenant isolation

Every row in contacts, opportunities, stage_history, and messages has a location_id column with Postgres Row-Level Security enabled. The app sets app.location_id as a session variable before each transaction; even a forgotten WHERE clause cannot leak data across sub-accounts.

8.2 Security

  • Webhook signatures: every incoming webhook is RSA-verified against GHL's published public key. Unsigned/invalid requests get a 401.
  • OAuth tokens: access tokens auto-refresh every 23 hours; refresh tokens rotate. Tokens are blanked on uninstall.
  • HTTPS only: all traffic terminates at Cloudflare's edge with an auto-renewing TLS certificate.
  • Logging: Bearer tokens and other secrets are explicitly redacted from logs.

8.3 EU data residency

All processing + storage happens on a single EU-region (Germany) server in Netcup Nuremberg. Cloudflare's edge serves the TLS handshake from the nearest EU PoP. No customer data leaves the EU at any point.

8.4 Reliability

What might go wrongHow the system handles it
Server unexpectedly restartsThe app comes back up automatically within seconds — no manual intervention needed, also after a full server reboot.
GoHighLevel sends the same event twice (their retries)We recognise duplicates and ignore the second copy. Your database never has double rows.
Authentication token expiresWe renew it in the background before it expires. You never notice.
Brief network hiccup or GHL outageThe event is still recorded with whatever data we received; the next event fills in any missing details automatically.
A webhook gets lost (rare)A daily safety-net process catches anything that slipped through, so nothing is permanently missed.

9. Next steps

9.1 Database backups Pending

Enable daily automatic backups of the Supabase database so a full point-in-time restore is always available. Two layers, used together:

  • VM-level snapshot — taken automatically by the hosting provider every night, retained for at least 7 days.
  • Database dump to off-site storage — a daily Postgres dump uploaded to an EU-region storage bucket as a second copy, in case the entire VM is ever lost.

Together, this means even a worst-case loss of the entire server still has a clean recovery path within 24 hours of any incident.
