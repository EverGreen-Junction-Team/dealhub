PipelinePulse

Stage Velocity & Stalled Deal Alerts for GoHighLevel

Project type: Public GHL Marketplace app (SaaS, multi-tenant)  ·  Stack: Node.js + MongoDB + React  ·  Target launch: ~5 weeks from kick-off  ·  Status: Planning  ·  Owner: Vaultsuite Team

1. What we're building

GHL's native pipeline view shows you where every opportunity is, but never how long it's been sitting there or how fast it's moving compared to history. PipelinePulse fills that gap.

It silently tracks every stage change in the background, computes per-stage velocity metrics, and pings the team when a deal stalls past a configurable threshold. The result: agencies and their sales teams get pipeline visibility GHL doesn't ship natively, plus actionable "this deal is going cold" alerts in Slack / email / SMS.

This is a productized, multi-tenant version of the stage-history pipeline we built for the convoVault client — distributed as a public Marketplace app with self-serve onboarding, monthly SaaS billing, and an embedded dashboard inside GHL.

3. Target customer

  • Primary: GHL agencies running 5–50 sub-accounts, where each sub-account has an active sales pipeline and the agency owns workflow / training. They feel the pain across multiple clients and will pay per sub-account.
  • Secondary: Single-tenant SMB GHL users (real estate, dental, home services) with one busy pipeline who want "stalled deal alerts" without building it themselves.
  • Not the target: Solo users with < 20 opportunities total — the pain is too small to pay for.

4. Core features (V1)

4.1 Stage History Tracking (the engine)

  • Subscribe to GHL webhooks on install: opportunity_stage_updated, opportunity_created, opportunity_deleted
  • Forward-only tracking — we capture everything that happens after the moment of install. No historical replay, no backfill. Day-1 dashboards look sparse by design; they fill up as the pipeline moves.
  • For every event, record one row in stage_history (one row per stage occupancy)
  • Daily sweep for orphan opportunities (created but never moved since install)
  • Idempotent — safe to replay webhooks without dupes

4.2 Dashboard (embedded inside GHL via a custom menu link)

  • Pipeline overview: opportunities per stage, with avg time-in-stage beside the count
  • Stage funnel: conversion rate between consecutive stages
  • Stalled list: every opportunity currently sitting > threshold in its stage, sortable, with one-click "open in GHL" links
  • Lost reason breakdown: grouped frequency of lost-reasons
  • Per-rep view: filter everything above by assigned user

4.3 Alerts

  • Stalled deal alerts: configurable threshold per stage (e.g. "alert if anything sits in Negotiation > 7 days"). Delivery: Slack, email, SMS (via the sub-account's own GHL SMS quota).
  • Daily digest (optional): single morning email listing every deal that crossed threshold yesterday
  • Weekly pipeline health email to the agency owner

4.4 Settings

  • Per-stage stalled-deal threshold (days)
  • Per-stage alert recipients
  • Enable / disable individual alert types
  • "Pause alerts" toggle (holidays)

5.2 Multi-tenancy

  • Every MongoDB document has a locationId field
  • A Mongoose middleware automatically injects { locationId: req.locationId } into every query — no place in the code can forget the tenant filter
  • Embedded UI requests carry a JWT signed at OAuth-callback time containing the location ID; backend pulls it off the JWT and pins it to the request before any query runs
  • This is the exact same multi-tenant pattern convoVault uses today (battle-tested)

5.3 Reused from convoVault (zero rebuild)

  • Stage history walker logic (opportunities walk, ghost-opp synthesis, message bucketing)
  • GHL API client with retry / rate-limit handling
  • Custom-field resolution pattern
  • Data cleaning helpers (email body strip, emoji strip)
  • MongoDB + Mongoose setup, multi-tenant locationId middleware, connection pooling

6. How the Alert Engine works (plain English)

The alert engine is the bit that converts "data sitting in the database" into "Slack message your sales team actually sees." Here's a worked example so the team has a shared mental model.

Setup: the agency configures one rule: "alert me when any deal sits in the 'Negotiation' stage for more than 7 days."

Day 1, 10:00 AM
Deal "Acme Corp" moves into Negotiation. GHL fires a webhook → we record it in the database. No alert yet — it's been there 0 days.
Day 2 – Day 6
Nothing happens externally. The alert engine wakes up every 15 minutes, scans the database, asks "anyone stuck > 7 days?" — finds no one — goes back to sleep.
Day 7, 10:04 AM
Acme Corp has now been in Negotiation for 7 days. Threshold crossed.
Day 7, 10:15 AM
Alert engine wakes up (the next 15-min tick). Scans: finds Acme Corp. Checks "have we already alerted on this one?" — no. Sends Slack message: "🚨 Acme Corp has been in Negotiation for 7 days. No movement." Marks the alert as sent so we don't spam every 15 min.
Day 7, 10:30 AM
Engine wakes up again. Acme Corp still stuck — but "alert already sent" → skip. No spam.
Day 8
Salesperson sees the Slack alert, calls the client, deal moves to "Closed Won". GHL fires a webhook → we record the move. Acme Corp is no longer in Negotiation → no future stalled-alert risk for this deal.

So what does "cron every 15 min" mean?

A small background script runs by itself every 15 minutes — no human triggers it, no UI clicks anything. Each run takes a few seconds and does three things:

  1. Look — query the database for any deals past their stage's threshold
  2. Filter — drop any deals we've already alerted on
  3. Fire — send Slack / email / SMS for whatever's left

Then it sleeps for ~14 min 59 sec and does it again.

Why 15 minutes and not real-time? A deal stuck for 7 days doesn't care if it's flagged at 10:04 AM or 10:15 AM. Running every minute would be 96× more database scans per day per customer — most finding nothing. 15 minutes is the standard "good enough" cadence; it's a one-line config change if we want to tune it later.

9. Out of scope (V1)

  • Forecasting / AI deal-scoring (Phase 5+)
  • Custom report builder (use the dashboard, then export CSV)
  • Mobile push notifications (Slack / SMS / email cover it)
  • Cross-CRM support (HubSpot, Salesforce, Pipedrive)
  • Public REST API for customers (V2)
  • Historical backfill of any kind — we track only what happens after install. Anything in the pipeline before install is invisible to PipelinePulse until it next moves.
  • White-label custom-domain (Agency tier only, V2)
  • Heavy regulatory compliance (UK / EU data residency, SOC 2, HIPAA, ISO 27001). This is a general-market SaaS — not a regulated-client build like convoVault. V1 ships the minimum required by the Marketplace listing: a privacy policy, basic terms of service, and a "delete-on-uninstall" hook that wipes the sub-account's data when the app is removed.
