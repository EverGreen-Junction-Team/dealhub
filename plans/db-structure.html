01The four business tables

Everything an analytics query hits day-to-day is in these four tables. All four are scoped by location_id (one per GHL sub-account — Crittall, BGD, Veritas, Omnia) with Row-Level Security enforcing tenant isolation.

contacts Core Primary key: (location_id, contact_id)

One row per person we've ever seen. Populated on first contact and updated whenever GHL sends us contact-level changes. Rich custom-field data lives in the custom_fields JSONB blob; the columns above it are the fields we've promoted for direct querying.

ColumnTypeWhat it means
location_id PKTEXTGHL sub-account. One of Crittall / BGD / Veritas / Omnia.
contact_id PKTEXTGHL's unique contact ID.
gclidTEXTGoogle Ads click ID — the token that lets us send Won deals back as offline conversions. Currently thin (~4 populated). Blocker on marketing loop.
gbraid, wbraidTEXTConsent-mode privacy-safe click identifiers (Google's app↔web equivalents of gclid).
gad_sourceTEXTWhich Google surface produced the click (Search, Display, YouTube, …).
utm_source, utm_medium, utm_campaign, utm_content, utm_termTEXTStandard UTM tags captured by the website's hidden form fields.
marketing_consentBOOLEANNurture-marketing opt-in state at the moment the contact was created.
custom_fieldsJSONBFull GHL custom-field dictionary as key→value (friendly keys). Every non-promoted contact custom field is in here.
from_backfillBOOLEANTRUE if this row was created by the one-time historical backfill; FALSE if by the live pipeline.
imported_at, updated_atTIMESTAMPTZWhen we first saw the row, and when we last touched it.
opportunities Core Primary key: (location_id, opportunity_id) · FK → contacts

One row per deal. The "deal card" as it exists in GHL, promoted into columns for querying. MEDDIC fields (1–10) are the rep-entered qualification narrative. The AI extraction (Phase 2) will add paired meddic_N_ai and meddic_N_evidence fields alongside these.

ColumnTypeWhat it means
location_id PKTEXTSub-account this deal belongs to.
opportunity_id PKTEXTGHL's unique deal ID.
contact_id FKTEXTThe person this deal is with. Joins to contacts.
nameTEXTOpportunity display name.
pipeline_id, pipeline_nameTEXTWhich pipeline the deal sits in (one pipeline per sales manager).
current_stage_id, current_stage_nameTEXTLive stage — updated on every stage change.
first_stage_id, first_stage_nameTEXTStage the deal was in the first time we saw it. Written once, never overwritten. Answers "where did this deal start?"
statusTEXTopen / won / lost / abandoned.
monetary_valueNUMERIC(12,2)Deal value in £ — entered by the rep at quote time.
assigned_toTEXTGHL user ID of the sales manager who owns the deal.
assigned_to_nameTEXTHuman-readable name of the owner (resolved by enrichment).
meddic_1 … meddic_10TEXTThe ten rep-entered qualification fields (Project Scope, Pain, Main Contact & Fans, Final Approver, Budget, Timeline, Process, Decision Criteria, Deal Lost Reason, Deal Won Reason). Rep-authored — never touched by the AI.
client_typeTEXTHomeowner / Architect / Contractor / Developer — persona for analytics.
product_systemTEXTManufacturer / system (Crittall, Cortizo, Genosal, …).
product_typeTEXTProduct category (Bifold Door, Casement Window, …).
postcodeTEXTJob-site postcode (the address the work will happen at — not the contact's address).
first_contact_methodTEXTHow the customer first got in touch on this deal.
lead_source_opportunityTEXTThe marketing source of the deal — the attribution field analytics group by.
inquiryTEXTThe customer's original enquiry text, in their own words. Populated by one of four upstream workflow routes.
custom_fieldsJSONBFull GHL custom-field dictionary for the opportunity.
is_ghost, is_deletedBOOLEANJunk-exclusion flags. Analytics queries filter both to false.
from_backfillBOOLEANTRUE if backfilled; FALSE if from live pipeline.
created_at_ghlTIMESTAMPTZWhen the opportunity was created in GHL — the true lead-arrival timestamp.
imported_at, updated_atTIMESTAMPTZOur own tracking timestamps.
stage_history Core Primary key: id (UUID) · FK → opportunities

One row per stage the deal has been in. When a deal moves stage, the previous row's left_at is stamped, its current_stage flips to false, and a new row is opened with current_stage = true. This is the source of stage-duration analytics and the funnel view.

ColumnTypeWhat it means
id PKUUIDRow identifier. Referenced by messages.stage_history_id.
location_id FKTEXTSub-account. RLS scope.
opportunity_id FKTEXTDeal this stage row belongs to.
contact_idTEXTCustomer this stage row belongs to (denormalised for fast joins to messages).
stage_id, stage_nameTEXTWhich stage this row represents. stage_name is snapshot at the moment — even if the stage is later renamed, historical analytics stay coherent.
pipeline_id, pipeline_nameTEXTWhich pipeline the deal was in at the time.
entered_atTIMESTAMPTZWhen the deal entered this stage.
left_atTIMESTAMPTZWhen it left. NULL if this is the current open stage row.
in_stage_duration_secondsINTEGERTime spent in this stage. Computed when the row closes.
current_stageBOOLEANTRUE for the one open row per deal at any given time.
deletedBOOLEANTRUE if the row was closed by an opportunity deletion (not a normal transition).
ghost_opportunityBOOLEANTRUE if this row was synthesised by the orphan sweep (no observed webhook created it).
product_system, product_typeTEXTSnapshot of the deal's product info at the moment of this stage change.
custom_fields_snapshotJSONBFull snapshot of the opportunity's custom fields at the time. Lets us answer "what was the product_type when this deal was at Sales Qualified?"
triggered_byTEXTProvenance: opportunity_created / opportunity_stage_updated / daily_sweep / backfill.
from_backfillBOOLEANTRUE if backfilled.
imported_atTIMESTAMPTZWhen we wrote the row.
messages Core Primary key: id (UUID) · Unique: (location_id, message_id) · FKs → contacts, opportunities, stage_history

One row per conversation message — email, SMS, WhatsApp, call, webchat. Deduped by GHL's provider message ID so re-fetches never duplicate. Cleaned body is what the LLM reads; raw body is retained for audit.

02Analytics views — one row per deal, all facts pre-joined

Two views layered on the four tables above. Designed so query tools (Claude, ad-hoc SQL) don't have to write joins every time.

vw_opportunity_flat View

One row per opportunity. The metrics table for everyday querying — funnel, business leaks, coaching benchmarks, pipeline risk. Joins contacts, opportunities, the open stage_history row, and per-opp message aggregates. Excludes deleted and ghost opportunities.

ColumnTypeWhat it means
location_id, opportunity_id, contact_idTEXTIdentity + tenant scope.
business_nameTEXTReadable label for the sub-account (Crittall / BGD / Veritas / Omnia).
opportunity_name, pipeline_id, pipeline_name, assigned_to, owner_nameTEXTDeal identity + routing.
lead_source_opportunity, first_contact_method, utm_source, utm_medium, utm_campaign, gad_source, has_gclidTEXT / BOOLSource attribution — from the linked contact where relevant.
product_system, product_type, client_type, postcode, inquiryTEXTDeal shape.
first_stage_name, current_stage_name, statusTEXTWhere the deal started, where it is now, whether it's still open.
current_stage_entered_atTIMESTAMPTZWhen the deal entered its current open stage.
days_in_current_stageNUMERICTime in the current stage, in days.
total_pipeline_age_daysNUMERICDays since the lead first entered the system (includes any marketing-pipeline dwell).
monetary_valueNUMERIC(12,2)Full deal value.
created_at_ghl, updated_at, last_activity_atTIMESTAMPTZDeal creation time, last update to the deal, latest message on the deal.
first_response_minutesNUMERICMinutes between deal creation and first outbound message — speed-to-lead proxy.
message_count, inbound_count, outbound_count, has_callINTEGER / BOOLMessage activity aggregates for the deal.
vw_opportunity_messages_json View

One row per opportunity. Full conversation for the deal assembled into a single JSONB blob, sorted ascending by timestamp — ready to hand to an LLM in one grab rather than rebuild from rows each time. Kept separate from vw_opportunity_flat because it's heavy; only joined when reading a deal's thread.

ColumnTypeWhat it means
location_id, opportunity_idTEXTJoin key back to vw_opportunity_flat.
message_countINTEGERTotal messages on the deal.
messages_jsonJSONBArray of {message_id, timestamp, direction, channel, body}, ordered by timestamp. Every message keeps its ID so the LLM can cite which one a fact came from.

03Internal tables — plumbing, not queried by analytics

Three internal tables run the sync itself. Analytics queries can ignore them.

installs Internal Primary key: location_id

One row per GHL sub-account that has installed the marketplace app. Holds the OAuth tokens the pipeline uses to call GHL APIs.

ColumnTypeWhat it means
location_id PKTEXTGHL sub-account.
company_idTEXTGHL agency ID above the location.
user_typeTEXT"Location" — indicates location-scoped install.
access_token, refresh_token, token_expires_at, scopesTEXT / TIMESTAMPTZOAuth credentials. Refreshed automatically 5 min before expiry.
installed_at, tracking_started_atTIMESTAMPTZFirst-install timestamps — never overwritten so historical analytics stay coherent.
reinstalled_atTIMESTAMPTZSet on any reinstall (NULL on first install).
uninstalled_atTIMESTAMPTZSet when the app is uninstalled; cleared on reinstall.
pending_opportunities Internal Primary key: (location_id, opportunity_id)

Deals that were created via webhook but haven't yet had a stage change. Emptied by the nightly orphan-sweep, which synthesises a stage_history row for anything that's sat here too long.

processed_events Internal Primary key: event_id

Every webhook we've handled, keyed by GHL's event ID. Lets us skip duplicate deliveries. Purged after 14 days by the same daily cron.

04How the tables relate

Join keys — for anyone writing SQL

contacts ↔ opportunities on (location_id, contact_id)

opportunities ↔ stage_history on (location_id, opportunity_id)

opportunities ↔ messages on (location_id, opportunity_id)

stage_history ↔ messages on stage_history_id (already denormalised — no extra join needed)

Everything is tenant-scoped by location_id. Row-level security enforces this at the database level; every query should still filter by location_id as a matter of habit.

Query pattern — the two "always start here"

Metrics query? Start from vw_opportunity_flat. It already has every deal fact pre-joined.

LLM context / conversation content? Join vw_opportunity_flat to vw_opportunity_messages_json on (location_id, opportunity_id). Filter to one opportunity — you get facts + full thread in one row.

A few gotchas to know about

Name collisions — contact.client_type (single-line, per contact) and opportunity.client_type (checkbox, per deal) both exist. Same for product_type. Also contact.first_contact_method (single underscore, how they contacted Crittall) vs opportunity.first_contact__method (double underscore, how they contacted us). Different meanings.

Filter junk — analytics queries should include WHERE is_deleted = false AND is_ghost = false on opportunities. vw_opportunity_flat already does this.

Empty inquiry is a data-quality flag — opportunity.inquiry is populated by one of four upstream workflow routes (website form, Crittall handover, webchat, enquiries@ inbox). An empty inquiry means the deal was created outside all four — usually a manual or imported deal.

Not covered here — Phase 2 additions still to come: 10× meddic_N_ai · 10× meddic_N_evidence · ai_extraction_meta · three whys · messages.recording_url · messages.transcript. These will be added to opportunities and messages as the AI extraction and call-transcription pipelines land.
